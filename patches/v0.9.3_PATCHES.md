# Function-KRO Adaptations for KRO v0.9.3

This document is the **upgrade guide** for re-applying function-kro's adaptations when upgrading to a new upstream KRO version. It is designed to be used by an agent following `UPGRADE_PROCESS.md` Phase 3.

For each adaptation, this document provides:
1. **What to look for** in the new upstream code
2. **What to do** (remove, replace, or modify)
3. **The complete function-kro code** where applicable, so you can reconstruct it even if upstream changed significantly
4. **Conditional guidance** for when upstream may have changed

Based on a full audit using `./scripts/diff-upstream-kro.sh -r v0.9.3`.

**The diff script skips `*_test.go` files**, so the audit counts below cover
non-test files only. Vendored tests are adapted too, and the ones that track an
adapted API are listed under [Test Files We Modify](#test-files-we-modify).

## Quick Reference

### Type Mapping (Upstream -> Function-kro)

Most upstream types (`Resource`, `ExternalRef`, `ForEachDimension`, `KRODomainName`) are now imported directly from the upstream `github.com/kubernetes-sigs/kro/api/v1alpha1` package and require **no replacement** during upgrades. Only the top-level wrapper type and schema-related types need mapping:

| Upstream Type | Function-kro Type | Notes |
|---------------|-------------------|-------|
| `*v1alpha1.ResourceGraphDefinition` | `*input.ResourceGraph` | Top-level input (our unique type) |
| `*v1alpha1.Schema` | Not used | Replaced by `xrSchema *spec.Schema` parameter |
| `v1alpha1.ResourceScope` | Not used | Crossplane manages CRD scope |

### Field Access Mapping

Anywhere upstream code accesses these paths, replace:

| Upstream Access | Function-kro Access | Notes |
|-----------------|---------------------|-------|
| `rgd.Spec.Resources` | `rgd.Resources` | No `Spec` wrapper |
| `rgd.Spec.Schema` | `xrSchema` parameter | Schema is a parameter, not nested in input |
| `rgd.Spec.Schema.Spec.Raw` | Not used | SimpleSchema not applicable |
| `rgd.Spec.Schema.Status.Raw` | `rgd.Status.Raw` | Status is top-level on ResourceGraph |
| `rgd.Spec.Schema.Types.Raw` | Not used | Custom types not applicable |
| `rgd.Spec.Schema.Group` | Not used | GVR from Crossplane |
| `rgd.Spec.Schema.APIVersion` | Not used | GVR from Crossplane |
| `rgd.Spec.Schema.Kind` | Not used | GVR from Crossplane |
| `rgd.Spec.Schema.Scope` | Not used | Crossplane manages CRD scope |
| `rgd.Name` | Not used | No CR name |
| `node.Meta.GVR` | Removed | Crossplane manages resource identity |
| `node.Meta.Namespaced` | Removed | Crossplane handles namespace scoping |

### Applying Mappings Globally

**IMPORTANT:** The Type Mapping and Field Access Mapping tables above must be applied **globally** across ALL functions in every modified file, not just the specific functions called out in the numbered adaptations below. When you encounter any reference to an upstream type or field path in any function, apply the appropriate mapping. The numbered adaptations below highlight the major structural changes, but simple type/field substitutions occur throughout.

### Guidance for New Upstream Fields

Since `Resource`, `ExternalRef`, `ForEachDimension`, and `KRODomainName` are imported directly from upstream, new fields on those types come automatically when bumping the `github.com/kubernetes-sigs/kro` dependency version. No manual field syncing is required.

For new fields on other types:

1. **Fields on `ResourceGraphDefinition.Spec`**: Evaluate -- our `ResourceGraph` has a flat structure (no `Spec` wrapper), so add directly to `ResourceGraph` if needed
2. **Fields on `Schema`**: Evaluate -- function-kro receives the XR schema as a `*spec.Schema` parameter, so Schema-level fields are typically not needed
3. **Fields that map to Crossplane concepts** (e.g., GVR): Skip -- Crossplane provides these via the function protocol

After adding new fields, update the Field Access Mapping table above and ensure `builder.go` accesses them correctly.

## Changes from v0.9.0 Adaptations

This section summarizes what changed in v0.9.3 compared to the v0.9.0 adaptation set, to help orient the reader.

### New Upstream Concepts in v0.9.3

- **`pkg/metrics` consolidation** (upstream #1227): the per-package `metrics.go` files in `cel/`, `runtime/` and `graph/schema/resolver/` were deleted and their collectors moved into `pkg/metrics`, which six vendored files now import. See [Adaptation 12](#adaptation-12-partial-vendor-of-pkgmetrics).
- **Author-defined status conditions** (upstream #1301 and follow-ups): a `conditions:` list in the instance status holds CEL expressions returning `runtime.newCondition(...)`. This brings `graph/conditions.go`, `runtime/conditions.go`, `cel/library/runtime.go`, a `Conditions` field on `graph.Node`, and an `InstanceConditionMetrics` feature gate. `cel/environment.go` registers the `runtime` variable and the Condition type provider unconditionally, and needs no adaptation.
- **`BuilderOption`**: `NewBuilder` gained `WithSchemaResolver` and `WithRESTMapper`. We evaluated and did not adopt them; see [Adaptation 1](#adaptation-1-builder-constructor-krographbuildergo).
- **`schema.*` allowed in status expressions** (upstream #1300): status expressions may now reference the instance's own schema, and `runtime.FromGraph` wires the instance node as a dependency of itself so the reference resolves. We inherit this.
- **External collection identity**: `resolveIdentity` no longer early-returns for `NodeTypeExternalCollection`; identity is now `metadata.namespace` plus `metadata.selector`, and `templateVarsForPaths` matches path prefixes. No adaptation needed.

### Adaptation Changes from v0.9.0

- **Adaptation 3 (instance node)**: shrunk considerably. Upstream now splits status handling into `buildStatusSchema`, `buildConditions` and `buildInstanceNode`, so we keep that decomposition instead of replacing it with one `buildInstanceNodeFromSchema`. Only the CRD-facing half goes: `buildStatusSchema` becomes `parseStatusExpressions`, which drops the inferred OpenAPI status schema.
- **Adaptation 5 (buildRGResource)**: shrunk. We now call `validateTemplateConstraints(rgResource, resourceObject, true, true)` rather than deleting the call, which keeps upstream's kro-owned label validation.
- **Adaptation 9 (validation)**: shrunk. We keep upstream's `validateResourceGraphDefinition` wrapper minus the Kind check, instead of folding it into `validateResourceIDs`.
- **Adaptation 10 (metadata)**: gone. `groupversion.go` is identical to upstream again. We used to delete `GetResourceGraphDefinitionInstanceGVR`; the function is unused here but harmless, and `flect` is a direct dependency of `fn.go` either way.
- **Adaptation 12 (metrics)**: new. Partial vendor of `pkg/metrics`.

## Adaptation 1: Builder Constructor (`kro/graph/builder.go`)

### What to look for

Upstream's `NewBuilder` takes Kubernetes client config and creates resolvers/REST mappers internally:

```go
func NewBuilder(clientConfig *rest.Config, httpClient *http.Client) (*Builder, error) {
    schemaResolver, err := schemaresolver.NewCombinedResolver(clientConfig, httpClient)
    // ...
    rm, err := apiutil.NewDynamicRESTMapper(clientConfig, httpClient)
    // ...
    return &Builder{schemaResolver: schemaResolver, restMapper: rm}, nil
}
```

### What to do

Replace the entire constructor. Remove `restMapper` from the `Builder` struct, and with it `BuilderOption`, `WithSchemaResolver` and `WithRESTMapper`.

v0.9.3 added those options, and they do not close the gap: `NewBuilder` still takes a `*rest.Config` and still builds a `DynamicRESTMapper` unless `WithRESTMapper` is also passed, and we have no resource scope information to build a mapper from. Injecting our resolver through `WithSchemaResolver` would leave us passing two nils and a fake mapper to reach the same place. Revisit this if upstream ever makes the REST mapper optional.

**If upstream still has a constructor taking `rest.Config`:** Replace it entirely with our version.
**If upstream changed the constructor signature but still uses Kubernetes clients:** Same, replace entirely.
**If upstream makes the REST mapper genuinely optional:** Prefer upstream's constructor with `WithSchemaResolver` and drop this adaptation.

### Function-kro code

```go
// NewBuilder creates a new Builder backed by the given schema resolver.
func NewBuilder(schemaResolver resolver.SchemaResolver) *Builder {
	return &Builder{schemaResolver: schemaResolver}
}

type Builder struct {
	// schemaResolver is used to resolve the OpenAPI schema for the resources.
	schemaResolver resolver.SchemaResolver
}
```

## Adaptation 3: Trim the Status Pipeline (`kro/graph/builder.go`)

### What to look for

Upstream builds the instance in five steps:

1. `buildInstanceSpecSchema()` builds the spec from SimpleSchema
2. `crd.SynthesizeCRD()` creates the CRD
3. `buildStatusSchema()` parses the status expressions, extracts the `conditions:` block, and infers an OpenAPI status schema from the CEL output types
4. `crd.SetCRDStatus()` puts the inferred status on the CRD
5. `buildInstanceNode()` assembles the node from those pieces

### What to do

Only the CRD half is unusable here, so keep upstream's decomposition and cut that half out:

- **Delete** `buildInstanceSpecSchema()` and the two `crd.*` calls. Crossplane owns the XRD.
- **Rename** `buildStatusSchema()` to `parseStatusExpressions()` and drop its schema half: it takes `statusRaw []byte` instead of `*v1alpha1.Schema`, no longer needs `bc`, and returns `(fieldDescriptors, statusTemplate, conditionExprs, error)` without the `*extv1.JSONSchemaProps`. Delete the CEL type inference loop and the `schema.GenerateSchemaFromCELTypes` call with it.
- **Keep** `buildConditions()` verbatim.
- **Keep** `buildInstanceNode()`, minus its `group`, `apiVersion`, `kind` and `namespaced` parameters and the `metadata.GetResourceGraphDefinitionInstanceGVR` call that used them.

Dropping the type inference loop does not lose type checking: `bc.compile` in the caller parses and checks each expression before building its program.

**Why not one replacement function?** We carried one until v0.9.3, and it silently missed upstream's change letting status expressions reference `schema.*`. Tracking upstream's shape means improvements inside these functions arrive with the copy instead of needing rediscovery.

**If upstream restructures again:** the invariant is that we need the parsed status expressions, their conditions, and the node. Anything producing an OpenAPI schema or touching a CRD is ours to drop.

### Function-kro `parseStatusExpressions` signature


## Adaptation 4: Replace `getSchemaWithoutStatus` (`kro/graph/builder.go`)

### What to look for

Upstream extracts the schema from a CRD, validates it has one version, converts `JSONSchemaProps` to `spec.Schema`, then removes status and conditionally adds namespace-less metadata for cluster-scoped CRDs:

```go
func getSchemaWithoutStatus(crd *extv1.CustomResourceDefinition) (*spec.Schema, error) {
    // validates CRD has exactly one version
    // converts JSONSchemaProps -> spec.Schema
    // removes status
    // adds metadata (namespace-aware)
```

### What to do

Replace with our simpler version that operates directly on `*spec.Schema`.

**If upstream changed `getSchemaWithoutStatus` but still takes a CRD:** Replace entirely.
**If upstream already takes `*spec.Schema`:** Just ensure status is removed.

**Note:** We do NOT inject `ObjectMetaSchema` here. Crossplane's `required_schemas` sends fully-flattened schemas with metadata already resolved. The CRD fallback path handles metadata injection separately in `crd_resolver.go`.

### Function-kro code (complete replacement)

```go
// getSchemaWithoutStatus creates a copy of the given schema with the status
// property removed. In function-kro, the schema comes from Crossplane (not a CRD),
// so we deep-copy it and strip the status field.
func getSchemaWithoutStatus(s *spec.Schema) (*spec.Schema, error) {
	if s == nil {
		return nil, nil
	}
	schemaCopy, err := schema.DeepCopySchema(s)
	if err != nil {
		return nil, fmt.Errorf("failed to deep copy schema: %w", err)
	}
	delete(schemaCopy.Properties, "status")
	return schemaCopy, nil
}
```

## Adaptation 5: Remove the REST Mapper from `buildRGResource` (`kro/graph/builder.go`)

### What to look for

Inside `buildRGResource()`, upstream asks the REST mapper for the resource's scope and GVR:

```go
mapping, err := b.restMapper.RESTMapping(gvk.GroupKind(), gvk.Version)
if err != nil { ... }
if err := validateTemplateConstraints(rgResource, resourceObject, mapping.Scope.Name() == meta.RESTScopeNameNamespace, instanceNamespaced); err != nil { ... }
```

and then sets `GVR` and `Namespaced` on the node from `mapping`.

### What to do

1. Delete the `RESTMapping()` call, and the `instanceNamespaced` parameter with it.
2. **Keep the `validateTemplateConstraints()` call**, passing `true, true` for the two scope arguments. Both scope branches inside it are then no-ops, which leaves its `validateNoKROOwnedLabels` check running. Deleting the call instead, as we did before v0.9.3, silently dropped that check.
3. Remove `GVR` and `Namespaced` from the `NodeMeta` initialization.

**If upstream adds new REST mapper calls:** remove those too, function-kro has no API access.

### Function-kro scope handling

## Adaptation 9: Validation Changes (`kro/graph/validation.go`)

### What to look for

Upstream has two validation entry points, both taking `*v1alpha1.ResourceGraphDefinition`:

- `validateResourceGraphDefinition()` validates the Kind name, calls `validateResourceIDs()`, then validates forEach dimensions
- `validateResourceIDs()` validates individual resource IDs

Also `validateIdentityFields()` reads `node.Meta.Namespaced`.

### What to do

1. **Keep both functions in upstream's shape.** Change the input type to `*input.ResourceGraph` and the field accesses per the Field Access Mapping table, and delete only the Kind check: our input has no schema of its own, because Crossplane owns the XRD and has already validated the XR's kind. Everything else, including where the `ErrNamingConvention` prefix is applied, stays where upstream puts it. We used to fold the wrapper into `validateResourceIDs`; that made the diff larger for no functional gain.
2. **Keep `validateTemplateConstraints()` unchanged.** [Adaptation 5](#adaptation-5-remove-the-rest-mapper-from-buildrgresource-krographbuildergo) calls it with constant scope arguments.
3. **Fix `validateIdentityFields()`**: replace `node.Meta.Namespaced` with `true`.

**If upstream renames these functions:** apply the same type changes to the new names.
**If upstream adds validation that needs the REST mapper:** remove that validation.

### Function-kro `validateResourceGraphDefinition`

```go
func validateResourceGraphDefinition(rgd *input.ResourceGraph, rgdConfig RGDConfig) error {
	err := validateResourceIDs(rgd)
	if err != nil {
		return fmt.Errorf("%s: %w", ErrNamingConvention, err)
	}

	// Validate forEach iterators after collecting all resource IDs
	resourceIDs := sets.NewString()
	for _, res := range rgd.Resources {
		resourceIDs.Insert(res.ID)
	}
	for _, res := range rgd.Resources {
		if err := validateForEachDimensions(res, resourceIDs, rgdConfig); err != nil {
			return err
		}
	}
	return nil
}
```

## Adaptation 13: Author-Defined Status Conditions (`fn.go`)

Upstream #1301 and its follow-ups let an author declare status conditions with CEL:

```yaml
status:
  conditions:
  - "${runtime.newCondition({type: 'X', status: 'True', reason: 'R', message: 'M'})}"
```

The graph and runtime halves are vendored unmodified. `parseStatusExpressions`
returns the `conditions:` block, `buildConditions` compiles it, `buildInstanceNode`
puts it on the node, and `runtime.Node.EvaluateConditions` evaluates it. What has
no upstream equivalent is the last step: standalone KRO writes conditions onto the
instance's `status.conditions`, while a composition function returns them to
Crossplane, which merges them into the XR.

`fn.go` closes that gap with `setAuthorConditions`, called after the desired XR is
set. It maps each `library.Condition` onto `response.ConditionTrue` / `False` /
`Unknown` with the author's reason and message. A condition whose expression cannot
resolve yet is left off the response rather than reported `Unknown`, matching how
unresolved status fields are skipped: the XR keeps whatever it already has. When an
expression fails outright, `EvaluateConditions` drops that one and returns the rest,
and we surface the failure with `response.Warning` instead of failing the render.

`EvaluateConditions` also takes the conditions to bind to `schema.status.conditions`
for `runtime.condition(schema, 'X')` lookups. Upstream passes kro's own instance
conditions, which do not exist here, so `observedXRConditions` passes the XR's
current conditions instead: Crossplane's `Ready` and `Synced`, plus any author
conditions merged in by earlier reconciles.

**If upstream changes the condition plumbing:** the piece to preserve is the mapping
onto the response. Everything before `EvaluateConditions` should stay upstream's.

### `kro/graph/schema/resolver/crd_resolver.go`

Resolves schemas by extracting them from CRD objects (fallback for older Crossplane).

```go
package resolver

import (
	"fmt"

	extv1 "k8s.io/apiextensions-apiserver/pkg/apis/apiextensions/v1"
	"k8s.io/apimachinery/pkg/runtime/schema"
	"k8s.io/kube-openapi/pkg/validation/spec"

	kroschema "github.com/crossplane-contrib/function-kro/kro/graph/schema"
)

type CRDSchemaResolver struct {
	schemas map[schema.GroupVersionKind]*spec.Schema
}

func NewCRDSchemaResolver(crds []*extv1.CustomResourceDefinition) (*CRDSchemaResolver, error) {
	schemas := make(map[schema.GroupVersionKind]*spec.Schema)
	for _, crd := range crds {
		if crd == nil { continue }
		group := crd.Spec.Group
		kind := crd.Spec.Names.Kind
		for _, version := range crd.Spec.Versions {
			if version.Schema == nil || version.Schema.OpenAPIV3Schema == nil { continue }
			gvk := schema.GroupVersionKind{Group: group, Version: version.Name, Kind: kind}
			specSchema, err := kroschema.ConvertJSONSchemaPropsToSpecSchema(version.Schema.OpenAPIV3Schema)
			if err != nil {
				return nil, fmt.Errorf("failed to convert schema for %s: %w", gvk, err)
			}
			if specSchema.Properties == nil {
				specSchema.Properties = make(map[string]spec.Schema)
			}
			specSchema.Properties["metadata"] = kroschema.ObjectMetaSchema
			schemas[gvk] = specSchema
		}
	}
	return &CRDSchemaResolver{schemas: schemas}, nil
}

func (r *CRDSchemaResolver) ResolveSchema(gvk schema.GroupVersionKind) (*spec.Schema, error) {
	return r.schemas[gvk], nil
}
```

### `kro/graph/schema/resolver/combined_resolver.go`

Combined resolver factories that pair Crossplane-provided schemas with core Kubernetes type resolution. These live in their own file so that upstream's `resolver.go` stays identical.

```go
// Package resolver provides schema resolution strategies for function-kro.
//
// This file contains function-kro additions that are not present in upstream KRO.
// These provide combined resolvers that pair Crossplane-provided schemas (or CRD-extracted
// schemas) with a core resolver for built-in Kubernetes types.
package resolver

import (
	"maps"

	"github.com/crossplane-contrib/function-kro/schemas"
	"k8s.io/apiextensions-apiserver/pkg/generated/openapi"
	"k8s.io/apimachinery/pkg/runtime/schema"
	"k8s.io/apiserver/pkg/cel/openapi/resolver"
	"k8s.io/client-go/kubernetes/scheme"
	"k8s.io/kube-openapi/pkg/common"
	"k8s.io/kube-openapi/pkg/validation/spec"
)

// NewCombinedResolverFromSchemas creates a schema resolver that combines
// a schema map resolver (for Crossplane-provided schemas) with a core resolver
// (for built-in Kubernetes types).
func NewCombinedResolverFromSchemas(schemaMapResolver *SchemaMapResolver) resolver.SchemaResolver {
	coreResolver := newCoreResolver()
	return &combinedResolver{
		primary:  schemaMapResolver,
		fallback: coreResolver,
	}
}

// NewCombinedResolverFromCRDs creates a schema resolver that combines
// a CRD schema resolver with a core resolver.
func NewCombinedResolverFromCRDs(crdResolver *CRDSchemaResolver) resolver.SchemaResolver {
	coreResolver := newCoreResolver()
	return &combinedResolver{
		primary:  crdResolver,
		fallback: coreResolver,
	}
}

// newCoreResolver creates a resolver for built-in Kubernetes types using
// compiled-in OpenAPI definitions. This handles types like Deployment, Service,
// ConfigMap, etc. that are part of the core Kubernetes API.
//
// It merges two definition sources into a single resolver so that $ref
// resolution works across both:
//   - generated definitions: common API groups (core/v1, apps/v1, batch/v1,
//     rbac/v1, networking/v1, policy/v1, storage/v1, autoscaling/v2, coordination/v1)
//   - apiextensions-apiserver definitions: CRD types, meta/v1 (ObjectMeta,
//     LabelSelector, etc.), and other apimachinery types
func newCoreResolver() resolver.SchemaResolver {
	return resolver.NewDefinitionsSchemaResolver(
		mergedOpenAPIDefinitions,
		scheme.Scheme,
	)
}

// mergedOpenAPIDefinitions returns OpenAPI definitions from both our generated
// definitions and the apiextensions-apiserver definitions. Our generated
// definitions take priority for overlapping types.
func mergedOpenAPIDefinitions(ref common.ReferenceCallback) map[string]common.OpenAPIDefinition {
	// Start with apiextensions-apiserver definitions (meta/v1, CRD types, etc.)
	merged := openapi.GetOpenAPIDefinitions(ref)
	// Layer our generated definitions on top (core/v1, apps/v1, etc.)
	maps.Copy(merged, schemas.GetOpenAPIDefinitions(ref))

	return merged
}

// combinedResolver tries resolvers in order until one returns a schema.
type combinedResolver struct {
	primary  resolver.SchemaResolver
	fallback resolver.SchemaResolver
}

func (c *combinedResolver) ResolveSchema(gvk schema.GroupVersionKind) (*spec.Schema, error) {
	s, err := c.primary.ResolveSchema(gvk)
	if err != nil {
		return nil, err
	}
	if s != nil {
		return s, nil
	}
	return c.fallback.ResolveSchema(gvk)
}

```

```go
// DeepCopySchema creates a deep copy of a spec.Schema by marshaling and

func DeepCopySchema(schema *spec.Schema) (*spec.Schema, error) {
	data, err := json.Marshal(schema)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal schema: %w", err)
	}

	}
	return &copy, nil
}
```

## Schema Resolution Architecture

Function-kro uses capability-based detection in `fn.go` to choose a schema resolution path. This is NOT in the KRO libraries -- it's in our `fn.go` entry point. But it's documented here because it explains why the adaptations above exist.

### Path 1: Required Schemas (Crossplane v2.2+)
```
HasCapability(REQUIRED_SCHEMAS) -> response.RequireSchema() -> request.GetRequiredSchemas()
    -> structToSpecSchema() -> SchemaMapResolver -> NewCombinedResolverFromSchemas()
    -> resolver.SchemaResolver passed to NewBuilder()
```

### Path 2: CRDs (Fallback for older Crossplane)
```
!HasCapability(REQUIRED_SCHEMAS) -> request CRDs via required_resources
    -> request.GetRequiredResources() -> NewCRDSchemaResolver()
    -> NewCombinedResolverFromCRDs() -> resolver.SchemaResolver passed to NewBuilder()
```

Both paths produce the same `resolver.SchemaResolver` interface that the graph builder consumes.

## Known Limitations

1. **No cluster-scope validation.** Upstream validates that cluster-scoped resources don't set a namespace (via REST mapper). Function-kro can't perform this check. Users setting namespace on cluster-scoped resources will get an error from Crossplane/the provider rather than from the function.

2. **No reactive watches on external references.** Upstream KRO added reactive watches (KREP-003) that re-reconcile instances instantly when an external resource changes. Function-kro fetches external refs via Crossplane's ExtraResources protocol (`RequiredResources`/`ResourceSelector`), which does not support watches — it only fetches the current state at function invocation time. Changes to external resources are picked up on the next reconciliation cycle, driven by the function's TTL or other events that trigger XR reconciliation.

3. **`runtime.condition(schema, 'X')` reads Crossplane's conditions, not kro's.** Upstream binds kro's own instance conditions (`Ready`, `InstanceManaged`, `GraphResolved`, `ResourcesReady`) so an author condition can read them. kro computes none of those here, so we bind the XR's current conditions instead. In practice a literal lookup only resolves for `Ready`, the one type both sets share, and it carries Crossplane's meaning of ready rather than kro's.

4. **Metrics are collected but never exposed.** The vendored collectors count expression evaluations, node resolutions and schema cache activity, but nothing registers them with a Prometheus registry, so the numbers go nowhere. Serving them would mean giving the function an HTTP endpoint, which nobody has asked for.

## Upstream Behavior We Intentionally Don't Need

1. **Namespace auto-defaulting (removed).** Upstream auto-defaults namespace from the instance for namespaced resources. We removed this (`normalizeNamespaces` in `runtime/node_resolve.go`) because Crossplane automatically sets the namespace on composed resources at the framework level. Composition authors don't need to set namespace in their resource templates.

2. **CRD synthesis (excluded).** Upstream generates CRDs from SimpleSchema definitions. Function-kro doesn't generate CRDs -- Crossplane manages the XR CRD lifecycle.

3. **Revision tracking (excluded).** Upstream tracks graph revisions with hashing and a registry. Function-kro is stateless per invocation -- no revision tracking needed.

4. **Instance condition events and telemetry (excluded).** The `InstanceConditionEvents` and `InstanceConditionMetrics` feature gates make the controller emit Kubernetes Events and Prometheus series on condition transitions. Both are controller-side, and both are off by default. Crossplane owns the XR's event stream.
